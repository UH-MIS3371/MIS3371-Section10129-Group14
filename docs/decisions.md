# MarketStreet — Decision Log

Important project decisions, with the reason for each. Add new decisions at the bottom. If a decision changes, add a new entry that replaces the old one instead of editing it.

> **Status:** D-1 to D-10 were drafted on 2026-10-10 during a documentation review, and the team has not recorded a formal approval. The built system follows all of them, as they are corrected by D-19. D-11 to D-20 describe how the code works now. If the team approves the list, add the names and the date here.

| # | Date | Decision | Why | Affects |
|---|---|---|---|---|
| D-1 | 2026-10-10 | **Only Market orders are executed.** Limit orders are rejected under the new rule BR-9, and the interface should not offer them. | The documents disagreed: the proposal said Limit was out of scope, the data dictionary said it was rejected, and the prototype executed it at the user's own price. A user-chosen price lets anyone create unlimited simulated cash. | BR-9, FR-1, FR-2, data dictionary `orderType` |
| D-2 | 2026-10-10 | **`userId` is a system ID taken from the signed-in session**, never entered by the user. Sign-in is required (FR-7). | main-transaction.md listed the user ID as a user input, while the data dictionary said it must not be trusted from the browser. | FR-7, main transaction, data dictionary |
| D-3 | 2026-10-10 | **Draft is a browser form state, not a status.** The official statuses stay at four: Submitted, Validated, Accepted, Rejected. | The state diagram showed five boxes, while the proposal and slides said four states. | State diagram, main transaction, proposal |
| D-4 | 2026-10-10 | **Cash, holdings, and the Accepted record are saved in one atomic commit, and BR-4 / BR-5 are re-checked inside it** with the account locked. | The workflow drew two separate saves, so a failure between them had no defined path. Checking funds only before the commit allowed two simultaneous orders to spend the same cash. | BR-4, BR-5, BR-7, workflow, state diagram |
| D-5 | 2026-10-10 | **System failures end as Rejected with `rejectionCategory = System`**; rule failures use `Rule`. No fifth status is added. | Audits and history must tell a broken rule apart from a system error, but adding a new status would change the four-status model the team has already presented. | BR-8, data dictionary, workflow |
| D-6 | 2026-10-10 | **A valid price is greater than $0 and no more than 15 minutes old.** | BR-6 said "valid price" without defining it, so it could not be tested. 15 minutes is a team choice and can be changed here. | BR-6, data dictionary `priceTimestamp` |
| D-7 | 2026-10-10 | **Transaction history shows both Accepted and Rejected trades.** | FR-4 and the user stories said every trade, but FR-6 said only completed ones. | FR-4, FR-6, user stories |
| D-8 | 2026-10-10 | **Money uses fixed-point decimals (or whole cents), never floating point.** | Floating-point math can make "exactly enough cash" (BR-4) fail. | Data dictionary money rules |
| D-9 | 2026-10-10 | **[Stakeholders.md](02-requirements/Stakeholders.md) is the single stakeholder list.** | The proposal and the stakeholder document listed different stakeholders. | Proposal, stakeholders |
| D-10 | 2026-10-10 | **Every new simulated account starts with $10,000.00 cash and no holdings.** This is what the live code does: `START_CASH_CENTS` is 1,000,000 and `START_SHARES` is empty in `aws/lambda/backend/market-data.js`. (The 10 AAPL / 2 MSFT / 1 IBM account belonged to the retired Week 8 backend in `archive/`.) | The data dictionary said the account "starts at the demo amount" without saying what that amount is. $10,000 matches the current prototype. | Data dictionary `cashCents`, `holdings` |
| D-11 | 2026-11-16 | **The role override is stored in the Users table.** | Cognito admin calls need IAM permissions that the AWS Learner Lab does not allow, so the Lambda keeps the role in `MarketStreetUsers`. | FR-11, data dictionary |
| D-12 | 2026-11-16 | **Scan is acceptable at class scale; per-user reads use GSIs** (trades by `userId` + `submittedAt`, games by `ownerId` + `updatedAt`). | A class-sized table is tiny, so a Scan is cheap and simple. Per-user lists should not scan. | Architecture, data dictionary |
| D-13 | 2026-11-16 | **The D-10 starting account ($10,000, no holdings) is fixed in code**, not chosen by users or admins. | A single constant keeps every new and reset account identical. | D-10, FR-10 |
| D-14 | 2026-11-16 | **`transactionId` is derived from `userId` + `requestId`.** The browser never chooses it. | A retried order maps to the same ID and returns the first result instead of trading twice. | IC-6, data dictionary |
| D-15 | 2026-11-22 | **The live site uses the production API `59w9sz4rrl` with Cognito sign-in on every route except the Learn quiz.** The test API stays only for the `cognito-login` and `platform-redesign` previews. | The live site could not load a portfolio because its API had no account routes and no `authorization` CORS header. Upgrading production fixed it. | aws/README.md, `frontend/app.js` |
| D-16 | 2026-11-22 | **The Learn quiz is public, and the server scores it.** | A quiz that needs no account is easy to try. Server-side scoring stops a browser from sending its own score. | `backend/learn.js`, `MarketStreetLearn` |
| D-17 | 2026-11-22 | **The Weekly League is a solo demo that runs in the browser.** One day opens per real day, and `?demo=1` lets a presenter advance days. | A shared league would need server tables and rules that Milestone 4 does not test. | `frontend/league.js` |
| D-18 | 2026-11-22 | **Rejected orders are saved as Rejected records, and the portfolio does not change (BR-8).** The Grader check page shows them. | Auditing needs to see why an order failed. | BR-8, `frontend/grader.js` |
| D-19 | 2026-11-27 | **Each order is saved once, with its final status: Accepted or Rejected.** Submitted and Validated are processing steps inside one Lambda call and are never written to the database. An Accepted order is saved in one DynamoDB `TransactWriteItems` call with the cash and holdings change. That write has a condition that re-checks cash (Buy) or shares (Sell). A Rejected order is saved with one `PutCommand`. DynamoDB does not lock the account; the conditional write does that job. This corrects the "status → Submitted / Validated" saves and the "locked account" wording in D-3, D-4 and the early design documents. | The design documents described four saves and a lock, but the code (`index.js` `postTrade`, `saveRejected`; `accounts.js` `commitTrade`) writes once per order. One write is simpler, and the condition still stops two orders from spending the same cash. The docs now match the code. | D-3, D-4, BR-4, BR-5, BR-8, workflow, state diagram, data dictionary `status` |
| D-20 | 2026-11-27 | **Short selling is out of scope for the main trade, but the Challenges game supports it.** BR-5 still forbids selling shares you do not own in the paper-trading account. Scenario Mode (Challenges) has its own Short option and its own game money in `MarketStreetGames`. | The scope note said "no short selling" while the Challenges game offers Short, which looked like a contradiction. The two use separate rules and separate data. | Requirements scope note, business problem, BR-5 |
